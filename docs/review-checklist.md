# 审查清单（review-checklist）

> 用途：任何「审查 / 盘点 / 缺口分析」类文档或会话结论，在写下结论前逐条过本清单。
> 本清单只规定**结论的证据门槛**，不规定审查范围与格式。

## 硬性要求

### R1. 「缺口 / 断链 / 缺失」类结论必须附数据佐证

凡写下「X 缺失 / X 断链 / X 不存在 / X 未接入 / X 未实现」类结论，**必须**附以下至少一项：

- **实测记录**：真实调用 / 真实点击 / 真机或浏览器走查的请求与响应证据（状态码、响应体、截图、日志行）；
- **库表计数**：对所指资源的数据库计数或内容抽查（如 `SELECT COUNT(*) ...`，注明查询时点）。

**不得仅凭空态或代码阅读下结论**。具体禁令：

- 不得把「列表为空 / 页面无数据」当成「功能不存在」——空态可能是**空库**而非没入口（2026-11-05 危机日志误报）；
- 不得把「grep 某文件未命中」当成「全链路不存在」——先确认页面/路由/契约/事件产线各环节，再下断链结论；
- 不得把「某类未被读取」当成「能力未挂主链路」——先查全部读取点与运行时行为（2026-11-05 推荐回灌误报）；
- 不得把「文案提到某去处」当成「该去处不存在」——先实际导航一次（2026-11-05 notice 文案误报）。

代码阅读结论可以写，但定性只能是「**静态存疑**」，并须标注「待实测」；凡升级为「断链 / 缺失 / P0 缺口」措辞，必须先补 R1 证据。

### R2. 已订正结论不删原文

被推翻的结论保留原文，在结论处加订正块（格式：`【已订正 · 日期】原结论不成立/已闭合。实测证据：…。订正人：…`），并在文档顶部「已订正结论索引」登记一行（结论 / 一句话原因 / 订正日期 / 证据所在批次或 commit）。索引比正文订正块更重要——先维护索引。
