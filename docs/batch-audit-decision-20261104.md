# 批量审核端点评估与判断（I3，2026-11-04）

> 任务来源：审核链路后端缺口 I3——「先给判断，不急着做」。
> 结论先行：**现阶段不做批量审核端点**。本文给出两套候选方案、代价评估与最终判断。

## 1. 结论：不做，且这个判断本身就是答案

审核（work/comment 的发布/下架/隐藏）是**人工内容决策**，不是机械操作。
批量端点的产品语义是「一串内容共享同一个判断」，这与审核的存在意义直接冲突：

1. **审核的价值在于逐条注意力。** 评论/作品是否「含不当内容」高度依赖上下文
   （同一句话在不同作品下含义不同）。批量通过/隐藏等于把 N 个判断压缩成 1 个，
   平台方要对「批量误杀」承担全部责任，且无法向用户解释「你的内容为什么被处理」。
2. **驳回理由（I1 刚落地）使批量更不成立。** 驳回必须带理由，而理由应当是因内容而异的；
   「N 条共享一个理由」等于对 N 个用户说同样敷衍的话，比没有理由更伤信任。
3. **当前量级不需要。** 待审队列（I2 实测返回）是个位数到几十条/天，
   人工逐条处理是分钟级工作量；批量端点节省的时间抵不上误操作风险。
4. **风险不可逆。** 批量隐藏会把一组公开内容同时撤下，恢复是 N 倍人工；
   而逐条慢速审核的最坏代价只是延迟。

## 2. 如果未来量级上来，两套候选方案（备查）

### 方案 A：事务型批量（全成或全败）

- 语义：`POST /api/admin/comments/batch-review { ids: [...], status, reason }`，
  单事务处理，任一失败整体回滚。
- 乐观锁 `expectedStatus` 的表达：批量下无法对每条独立传 expected，
  只能统一「当前必须全部处于 status=0（待审）」，任一条已变化即整体 3001。
- 优点：无中间态；缺点：一条被他人抢先处理，整批失败，管理员等于白点。
- 代价：中（事务 + 锁行 + 通知逐个落库）；风险：**整批失败的挫败感会倒逼管理员放弃复核直接全批通过**，比没有批量更糟。

### 方案 B：逐条结果型批量（部分成功）

- 语义：同一请求处理 ids 数组，返回 `results: [{id, code, message}]`，
  每条独立事务（成功的不回滚）。
- 优点：与人工审核节奏兼容（能跳过冲突项）；缺点：响应体大、
  部分失败的重试需要前端做差集，误操作面与逐条相同但速度快了——
  **速度快恰恰是缺点**：降低了每条内容获得的注意力。
- 代价：中高；风险：同方案 A 的「注意力压缩」。

## 3. 触发重估的条件

只有同时满足以下条件才应重新评估批量端点：

1. 日均待审 > 200 条且稳定两周以上（人工逐条成为真实瓶颈）；
2. 队列中存在**客观同构**的类别（如纯广告链接、明确机器刷量），
   这些类别由 AI 审核辅助（路线图 P2-1）先分层，人工只确认分层结果；
3. 批量操作仅开放给「同类别 + 同理由」集合，且沿用 I1 的理由必填约束
   （批量理由 = 该类别的判定说明，不允许空泛）。

在此之前，批量审核端点**明确不做**；审核工作台优化方向是
「队列信息密度」（I2 的对象级审计摘要）而不是「点击次数减少」。
