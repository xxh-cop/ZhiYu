## 4. 瓶颈定位（实测 → 推断分级）

**实测证据**：
1. 后端日志中 c=20 全程只出现 `sse-1`～`sse-4` 四个线程名——`SseExecutorConfig`
   corePoolSize=4、maxPoolSize=16、queueCapacity=100。Spring `ThreadPoolTaskExecutor`
   的扩容顺序是 core → 队列满 → 才扩到 max，因此**实际并发恒为 4**，max=16 是摆设。
2. c=20 尾部请求首 chunk ≈ 3.4–4.8s ≈ 等 2–3 轮「4 并发 × 单轮生成 ~1.2s」，与排队模型吻合。
3. 零上游限流、零 HTTP/SSE 错误——DeepSeek 侧与 Tomcat 连接层都不是瓶颈。

**推断（未单独实测）**：
- Spring AI WebClient 的连接池上限未核查，若其为默认（500）则不是瓶颈；若要上 50+ 并发需单独验证。
- 单机内存模式下熔断/心流统计无跨进程竞争；多实例部署需重测。

## 5. 结论与调优建议

**NFR-02「AI 首字 ≤2s」**：在低并发（≤5，试点期单人体验口径）**达标**；
按 NFR-03「100 人在线」类推的并发对话口径下 **10 并发临界、20 并发不达标**。
建议在需求文档中把 NFR-02 的验收口径明确为「并发 ≤5 时 P95 ≤2s」，
或按下面建议消化并发能力后再按原口径验收。

| 优先级 | 建议 | 预期收益 | 风险 |
|---|---|---|---|
| P0 | `sseExecutor` 改为 core=max=16（或 queue 降到 ~20 让 max 生效），消除「假 max」 | c=10 尾延迟基本消除，c=20 P95 回到 ~2.5s | 上游 DeepSeek 并发限额未知，需先小额验证 |
| P1 | NFR-02 验收口径写清并发数（建议「≤5 并发 P95≤2s，20 并发 P95≤5s」双档） | 避免口径争议 | 无 |
| P1 | 增加排队可观测：sseExecutor 暴露 activeCount/queueSize 到 /api/admin/ops/health | 压测与生产可定位排队 | 小 |
| P2 | 试点前与 DeepSeek 确认并发/QPS 限额，必要时加出站限流（宁可排队不可 429） | 防止上游限流突变 | 无 |

# 修复后（2026-11-03）

> 修复内容：`SseExecutorConfig` 由 core=4 / max=16 / queue=100 改为 **core=max=16 / queue=32**，
> 参数外置到 `application.yml` 的 `zhiyu.sse.executor.*`（环境变量 `ZHIYU_SSE_CORE_SIZE` /
> `ZHIYU_SSE_MAX_SIZE` / `ZHIYU_SSE_QUEUE_CAPACITY` 可覆盖），消除「假 max」。
> 选型理由：Spring 线程池扩容顺序是「core 满 → 入队 → 队列满才扩线程」，core=max=16 让
> 16 条线程常驻、并发请求立即获得线程；queue=32 仅作超过 16 并发时的短突发缓冲；
> 再超出走 CallerRunsPolicy 由 Tomcat 线程兜底，宁可变慢不丢弃 SSE 请求。
> 结论先行：**四个并发档全部达标（P95 ≤ 2s），20 并发 P95 从 4506ms 降至 1818ms，零错误。**

## D. 剩余瓶颈与边界（不夸大）

- 20 并发是本线程池设计的满配点（16 线程 + 突发缓冲），**>16 并发的持续负载未验证**；
  再上量前需先确认 DeepSeek 并发/QPS 限额，并核查 Spring AI WebClient 连接池上限。
- 本轮为单机回环 + 家庭宽带出口 → DeepSeek 云端，不代表多实例 / 生产网络表现。
- 单机 memory 模式熔断/心流统计无跨进程竞争；多实例部署需切换 redis store 并重测。
